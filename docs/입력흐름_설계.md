# 재고 입력 흐름과 후속 설계

## 확인된 요구사항

- 지점과 영업 날짜를 달력에서 선택한 뒤 카카오톡 메시지 본문을 붙여넣는다.
- 한 번에 한 지점의 오픈 또는 마감 보고 한 건을 처리한다.
- 본문에 월·일만 있으면 선택 날짜의 연도를 사용하고, 날짜가 없으면 선택 날짜를 사용한다.
- 날짜 또는 알려진 본문 지점과 선택값이 다르면 미리보기와 저장 확인창에서 알린다. 날짜는 해석된 보고 날짜, 지점은 선택 지점에 저장한다.
- 미리보기 후 선택 지점·날짜가 달라지면 보고 내용 확인을 다시 실행해야 한다.
- Excel은 한 지점을 선택하고 여러 날짜를 등록한다. 현재 필수 헤더는 `날짜`, `상품명`, `오픈재고`, `잔여재고`다. 사용자가 보낸 4열 예시는 이 헤더를 붙이면 기존 파서와 호환된다. 헤더 없는 파일을 자동 추정하지 않는다.
- 표준상품명 사전은 검증한 v2를 유지한다. 과거 HTML의 사전으로 되돌리지 않는다.
- 재고 조회·수정 및 텍스트·Excel 입력이 우선이고 로그인은 다음 단계다.
- 대표님은 전체 지점 판매현황 대시보드를 사용하고 직원은 보고를 입력한다. 직원의 조회·수정 범위는 미정이다.

## 현재 변경의 범위

`parsers/reportContext.js`는 선택값과 본문 문맥을 비교한다. `App.jsx`가 경고를 표시하고 저장 직전 선택값 변경을 검사한다. 이 코드는 브라우저에서 실행되며 백엔드가 아니다. 지점 검사는 알려진 지점명이 단독 줄로 적힌 경우를 대상으로 하며, 알 수 없는 지점명이나 자유로운 문장의 지점명은 자동 확정하지 않는다.

## DB 회의 후 연결할 설계 초안

입력별 파서 → 공통 상품명 표준화·검증 → 미리보기 → 저장 전 재검증 → 저장소 접근 순서로 역할을 분리한다. 실제 서버 실행 환경, API 경로, 테이블 구조는 아직 확정하지 않는다. 서버를 도입하면 클라이언트 검증 결과를 신뢰하지 않고 날짜·지점·수량·중복 및 권한을 다시 검사해야 한다.

조회·수정 서비스와 저장소 접근의 경계를 먼저 정하고, DB 설계가 나오면 실제 연동을 구현한다. 예측 수식과 DB 스키마는 담당 팀원과 협의한다. 로그인 단계에서는 인증 사용자와 허용 지점을 연결하고 대표님 전용 조회 권한을 적용한다.

## 검증

`node scripts/verify-report-context.mjs`로 사용자 예시와 문맥 비교를 검증한다. `scripts/verify-split.mjs`는 최초 분리 당시의 코드 동일성 검사이므로 이후 의도적인 기능 변경에는 실패할 수 있다. DB 쓰기를 수행하는 검증은 포함하지 않는다.
